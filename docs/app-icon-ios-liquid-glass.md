# App icon 與 iOS 26 Liquid Glass

iOS 26 會對主畫面 icon 套用 Liquid Glass：反射、折射、陰影、模糊與高光。原生 App 透過 Icon Composer 提供分層 `.icon` 並以 Xcode 26 編譯，可以指定 foreground／mid-ground／background layer、depth 與 specular highlight。

**PWA 拿不到分層。** 只能交付單張點陣圖，所以天花板是「系統對單張圖的自動推導」，實際效果是邊緣的立體處理，不是原生 App 那種可控的玻璃分層。要拿到可控效果只有轉原生 App 一途，那遠超出 icon 調整的範圍。

本文記錄實機量到的觸發條件與設計限制。產出指令與工作流程見 [README 的 App icon 產出流程](../README.md#app-icon-產出流程)；這次改版的變更清單見 [完成紀錄](completed-references/app-icon-ios-liquid-glass.md)。

---

## 1. 兩個觸發條件

### 1.1 圖檔必須是透明背景

iOS 把不透明像素當成 icon 的**前景層**，自己補背景與立體光影。圖檔自帶不透明底等於宣告「整張圖都是前景」，系統就不做加工。

最直接的證據：一個有玻璃感的對照 PWA，它的 `apple-touch-icon.png` 裡完全沒有深色背景（四角與中心 alpha 皆為 0），但主畫面實拍就是深底加邊緣光影 —— 那個背景只可能是系統生成的。

### 1.2 圖形必須夠細，不能填滿

透明是必要條件，**但不充分**。主體內部一旦填滿，效果就完全消失。

這與填色的 alpha 無關：半透明 20% 與不透明深青色分別實測，結果相同。決定成敗的是**那塊區域有沒有被蓋住**，不是蓋住它的顏色有多透明。

造型因此必須是描邊加小面積實心色塊（線稿），不能是面狀填色的剪影。

## 2. 覆蓋率：一個代理指標，不是規格

`apple-touch-icon.png` 的**全透明像素比例**是判斷 icon 會不會拿到加工的最便宜指標：

| 圖形 | 全透明像素 | 玻璃 |
|---|---|---|
| 改版前（不透明滿版底） | 0% | ❌ |
| 對照樣本（另一個 PWA 的線稿 icon） | 76.3% | ✅ |
| 大尺寸線稿，主體內部填滿（半透明 20%） | 約 62% | ❌ |
| 大尺寸線稿，主體內部填滿（不透明深青） | 62.2% | ❌ |
| 目前版本（線稿＋縫線＋錢幣＋星星） | 86.5% | ✅ |

**這是代理指標，不是機制。** 實機觀測到的因果是「**填滿主體內部會失效**」，比例只是它的副產品。兩者不等價：同樣是填滿口袋，目前這個較小的造型只會掉到 74.2%，而當初那個較大的造型會掉到 62% —— 前者從未在實機驗過，卻可能一樣失效。所以**先看有沒有面狀填色，比例當第二道防線**，不要倒過來。

已觀測的邊界：76.3% 與 86.5% 有效、62% 失效，**中間的 62–76% 是未驗證區**。

**細元素的成本很低。** 虛線縫線只吃掉 1.7% 的透明比例，小色塊（錢幣、星星）也在同一個量級。可以自由加細節，不能加面狀填色。

`npm run icons:generate` 每次都會印出這個比例，低於 76.3%（實測有效的最低值）就警告。它是煙霧偵測器，通過不等於保證有效 —— 造型有面狀填色時仍要實機確認。

## 3. 量測方法

**不能只看 `sips -g hasAlpha`。** 有 alpha channel 不等於有透明像素 —— 上面所有樣本都回報 `hasAlpha: yes`，實際差異只在像素值。必須讀實際的 alpha 分佈。

`scripts/generate-icons.mjs` 用 `sharp` 取原始像素直接統計，不需要 PIL 或 ImageMagick。要單獨檢查任何一張 PNG（例如別的 App 的 icon）可以照同樣方式做：讀 raw RGBA，數 alpha 為 0 與 255 的像素，並看四角與中心的值。

## 4. 已經驗證過、不要重跑的假說

| 假說 | 來源 | 實測結果 |
|---|---|---|
| manifest 的 `"purpose": "maskable"` 才會觸發自動玻璃化 | 第三方 PWA 平台說明文件 | **不成立。** 對照樣本的 icon 目錄裡沒有 manifest 也沒有 maskable 宣告，照樣拿到效果。manifest 的 `purpose` 只剩安全區裁切的價值 |
| 透明底在 Dark／Tinted 模式會糊掉，所以底色要維持不透明 | 一般 PWA icon 建議 | **方向相反。** 透明底正是拿到系統加工的關鍵。真正該擔心的是圖形本身是否依賴底色 |
| 任何部分透明度都會關掉效果 | 中途為了解釋填色失效而提出 | **不成立。** 對照樣本本身就有 12.7% 的抗鋸齒半透明像素（76.3% 全透明加 11.0% 全不透明），照樣有效。真正的變數是覆蓋率 |

## 5. 設計限制

- **不要把玻璃、陰影、反射烘進 PNG。** 那會破壞 Light／Dark／Clear／Tinted 四種外觀的系統適配，可能出現雙重高光。只交付乾淨平面圖形，立體感交給系統。
- **圖形不能依賴背景。** 沒有保證存在的底色，所以造型必須由不透明的描邊與實心色塊撐起，不能靠半透明填色。
- **描邊不要太粗。** 玻璃處理會沿著描邊擠出厚度並加高光，等於把粗細再放大一次。目前 `stroke-width="24"`（512 畫布的 4.7%）；更粗會在主畫面讀成一坨。
- **避開畫布四角。** iOS 的 squircle 遮罩會裁掉角落，放在那裡的元素會被切掉。
- **簡單形狀優於精細細節。** 細節多的圖在小尺寸會糊成雜點，而且系統加工對乾淨的向量形狀效果較好。

## 6. 各輸出的背景策略

背景由 `scripts/generate-icons.mjs` 的 `OUTPUTS` 表以 per-output 的 `flatten` 開關決定，不是全域行為：

| 輸出 | 背景 | 原因 |
|---|---|---|
| `apple-touch-icon.png` | 透明 | iOS 自己補背景與 Liquid Glass 光影 |
| `android-chrome-*.png` | 透明 | launcher 對 `purpose: "any"` 的 icon 會自行提供背景 |
| `favicon-*.png`、`favicon.ico` | `#1A1C2C` | 瀏覽器分頁列沒有系統補的背景，線稿會看不清 |
| `icon-maskable-512.png` | `#1A1C2C` | Android adaptive icon 的裁切沒有系統補的背景，透明會露空 |

## 7. 驗證方式

Liquid Glass 只能實機觀察，模擬器與桌面瀏覽器都無法代替。

1. **先移除主畫面上的舊圖示，再重新加入。** iOS 會快取 web clip icon，不移除就會看到舊圖而誤判成「沒生效」。這是最容易踩的坑，每驗一次都要做。
2. 比對 **Light／Dark／Clear／Tinted** 四種外觀。判斷標準是「邊緣是否出現立體處理」，以及四種外觀下圖形是否都清楚、沒有糊化或雙重高光。
3. 桌面瀏覽器 favicon 另外看，改動後如果沒變化，先硬重整或反註冊 service worker 再懷疑程式。

## 8. 已知限制

- **PWA 無法指定 Clear 外觀。**
- **16×16 favicon 會失去細節。** 縫線在該尺寸看不見，星星縮成角落的亮點。造型仍可辨識，但這是單一 SVG 來源產出全尺寸的固有代價；要救得讓 favicon 走自己的粗描邊來源，代價是造型變成兩個地方要維護。
- **產出檔直接進版控。** GitHub Pages 部署不跑 icon 產出步驟，所以改圖後必須手動跑 `npm run icons:generate` 並 commit 產出檔。
