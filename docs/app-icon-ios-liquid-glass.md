# App icon 與 iOS 26 Liquid Glass

iOS 26 會對主畫面 icon 套用 Liquid Glass：反射、折射、陰影、模糊與高光。**效果來自圖示的分層，不是來自透明度、覆蓋率或留白。**

原生 App 用 Icon Composer 交出分層 `.icon`（background／mid-ground／foreground），系統對每個前景層各自擠出厚度、打光、投影。所以背景層可以是 100% 不透明的滿版底，前景層可以是大面積實心色塊，兩者都不影響效果。

**PWA 拿不到分層。** web clip 只能交一張點陣圖，iOS 只能從 **alpha** 反推哪裡是前景。天花板是「系統對單張圖的自動推導」，效果遠弱於原生：拿到的是系統補的背景加描邊上的一點邊緣光。要拿到可控效果只有轉原生 App 一途。

本文記錄實機量到的條件與設計限制。產出指令見 [README 的 App icon 產出流程](../README.md#app-icon-產出流程)；上次改版的變更清單見 [完成紀錄](completed-references/app-icon-ios-liquid-glass.md)。

## 1. 分層才是機制

### 1.1 不透明滿版底照樣有玻璃——只要它是分層圖示

Slack、日誌、密碼、無邊記的背景層都是不透明滿版，前景是大面積實心色塊，覆蓋率接近 100%，而它們的玻璃感是整個主畫面最強的：

- 前景邊緣有 4–5px 的高光帶：日誌翅膀上緣由本體亮度 51 升到峰值 156 再回落到 111
- 前景對背景有投影，Slack 的白底由上到下 254 → 236，底部再回升到 240

### 1.2 不透明的**非分層**圖示完全拿不到加工

同一張截圖裡的 O'Reilly 是一張傳統平面 PNG，跟 Slack 一樣是白底方塊，但白底整條 255、上到下零變化，圖形邊緣 255 → 251 → 75 → 45 是 1px 硬切，沒有高光帶也沒有投影。

**iOS 26 不會對任意不透明圖示自動加工。**

> 這個樣本有一個沒排除乾淨的干擾：O'Reilly 那格帶著雲端下載標記。它的白底是滿值 255、沒有被壓暗，所以不是灰階佔位圖，但要更硬的證據，可以找一個確定沒改過 icon 的已安裝 App 再確認一次。

## 2. PWA 為什麼要交透明底

分層那條路走不到，alpha 就成了 iOS 唯一的線索：不透明像素當前景，其餘由系統補背景與光影。圖檔自帶不透明滿版底等於宣告「整張圖都是完稿」，就走 §1.2 那條路，維持全平。

直接證據：一個有玻璃感的對照 PWA，它的 `apple-touch-icon.png` 裡完全沒有深色背景（四角與中心 alpha 皆為 0），但主畫面實拍就是深底加邊緣光影。

**現場判準：** 沒拿到處理時 iOS 會把圖壓到**純白底**（量到 255）；拿到處理時背景是系統生成的**深色**（量到 0）。主畫面上一眼可辨，不必量像素。

## 3. 空腔內周長：目前最好的預測器

透明底是必要條件，但不充分。**決定成敗的是圖形圍住了多少透明區域，以及圍得多碎。**

### 3.1 定義

**空腔內周長 = 被圍住的透明像素中、至少有一個 4-鄰居是 ink 的數量 ÷ 畫布邊長**，單位是「畫布邊長」。

量法必須寫死，換一個定義數字就會偏：

- **ink = alpha ≥ 128。** 半透明填色算在透明那側，因為有一版 `fill-opacity 0.15` 的填色在實機上失效；門檻若設在 `alpha > 0`，那塊填色會被算成 ink、空腔歸零，那一筆就無法解釋。
- **4-connectivity**，非 8。
- **從畫布四邊 flood fill**：流得到的透明是 iOS 會替換掉的背景，流不到的才是空腔。
- **分母是畫布邊長**（不是像素總數）。

### 3.2 十五個樣本

三個互不相關的 icon 家族，同一支 iPhone：

| icon | 結果 | 空腔數 | 圍住的透明 | **內周長** |
|---|---|---|---|---|
| 實心剪影／實心圓（四張） | ✅ | 0 | 0.0% | **0.00** |
| 口袋輪廓，單一空腔 | ✅ | 1 | 10.0% | **1.12** |
| 目前版本 | ✅ | 1 | 13.0% | **2.63** |
| 口袋線稿，原尺寸 | ✅ | 1 | 14.1% | **2.71** |
| 口袋線稿，放大 1.21 倍 | ❌ | 1 | 21.6% | **3.20** |
| 另一個 PWA 的線稿 icon | ✅ | 5 | 13.9% | **3.24** |
| 口袋線稿，放大 1.62 倍 | ❌ | 1 | 43.1% | **4.19** |
| 口袋線稿，放大 1.74 倍 | ❌ | 1 | 50.4% | **4.47** |
| 同一輪廓，內部切成 16 格 | ❌ | 16 | 10.6% | **4.67** |
| 口袋線稿，放大 1.85 倍 | ❌ | 1 | 57.6% | **4.78** |
| 格線稿 icon | ❌ | 17 | 14.2% | **5.72** |
| 格線稿 icon，放大 | ❌ | 17 | 27.9% | **8.30** |

**十五筆只有一個逆序**（3.20 失效與 3.24 有效，差 0.04 等於平手）。

它為什麼吃得下兩種失效：**放大空心圖形會拉長內周長，把空腔切碎也會拉長內周長。** 面積與拓樸只是同一個量的兩種增長方式——同一個輪廓、面積不變、只把單一空腔切成 16 格，內周長從 1.12 跳到 4.67，效果就消失。

### 3.3 實用門檻

- **≤ 2.71 安全**（已驗證有效的最大值）
- **≥ 3.20 危險**（已驗證失效的最小值）
- **3.2 附近是重疊區，這個指標在那裡不決定**

`npm run icons:generate` 每次都會印出這個值，高於 2.71 就警告。**它是煙霧偵測器不是規格**——沒有任何機制解釋這個邊界，通過只代表「值得上機驗」。

## 4. 已經推翻、不要重跑的假說

| 假說 | 實測結果 |
|---|---|
| manifest 的 `"purpose": "maskable"` 才會觸發 | **不成立。** 對照樣本的 icon 目錄裡沒有 manifest 也沒有 maskable 宣告，照樣有效。iOS 讀的是 `apple-touch-icon` |
| 透明底在 Dark／Tinted 會糊掉，底色要維持不透明 | **方向相反。** 透明底正是拿到系統加工的關鍵 |
| 任何部分透明度都會關掉效果 | **不成立。** 對照樣本本身就有 12.7% 的抗鋸齒半透明像素 |
| 面狀填色不能被玻璃化 | **完全相反。** 四張實心圖形全部有效，實心是最安全的做法 |
| 全透明比例是門檻 | **不成立。** 61.3% 透明的實心圓有效，83.0% 透明的格線稿失效 |
| 圖形離畫布邊緣太近會失效 | **不成立。** 同一組線稿留白 22.8% 有效、17.8% 失效、11.7% 有效，非單調 |
| 覆蓋率高的 icon 一律沒有玻璃 | **不能外推。** 原生分層圖示覆蓋率接近 100% 照樣有效 |
| 描邊飽和度不夠會讓 iOS 生成淺色背景 | **不成立。** 飽和度 0.08 與 0.92 的同一造型都是白底；而拿到深底的樣本飽和度 0.86，比 0.92 低（來源：另一個專案的 git 歷史交叉比對 ＋ 同機並排實拍） |
| manifest 的 `background_color` / `theme_color` 影響底色 | **不成立。** 兩個專案都是深色宣告，一個拿到深底一個沒有（同上來源） |

## 5. 設計限制

- **首選實心造型。** 實心圍不出空腔，內周長恆為 0，離門檻最遠，而且不依賴門檻確切落在哪。線稿要控制在 2.71 以下，那個數字還沒被釘死。
- **要用線稿就別把空腔切碎。** 格狀分隔線是最貴的做法：面積不變也會讓內周長翻倍以上。
- **不要把玻璃、陰影、反射烘進 PNG。** 那會破壞 Light／Dark／Clear／Tinted 四種外觀的系統適配，可能出現雙重高光。
- **圖形不能依賴背景。** 沒有保證存在的底色，造型必須由不透明的描邊與實心色塊撐起。
- **描邊不要太粗。** 玻璃處理會沿著描邊擠出厚度並加高光。目前 `stroke-width="24"`（512 畫布的 4.7%）。
- **避開畫布四角。** iOS 的 squircle 遮罩會裁掉角落。以 `|x/a|^5 + |y/a|^5 = 1` 的超橢圓近似該遮罩，足以在產出前檢查。
- **簡單形狀優於精細細節。** 細節多的圖在小尺寸會糊成雜點。

## 6. 各輸出的背景與縮放

`scripts/generate-icons.mjs` 的 `OUTPUTS` 表以 per-output 開關決定，不是全域行為：

| 輸出 | 背景 | 縮放 | 原因 |
|---|---|---|---|
| `apple-touch-icon.png` | 透明 | 1 | iOS 自己補背景與 Liquid Glass 光影 |
| `android-chrome-*.png` | 透明 | 1 | launcher 對 `purpose: "any"` 會自行提供背景 |
| `favicon-*.png`、`favicon.ico` | `#1A1C2C` | 1 | 瀏覽器分頁列沒有系統補的背景 |
| `icon-maskable-512.png` | `#1A1C2C` | **0.83** | Android adaptive icon 可能被裁成 r = 0.4×邊長 的圓 |

**maskable 為什麼要單獨縮放：** 原尺寸下右上那顆星星的頂點在 (400,60)，離中心 243，超出 204.8 的安全圓。改縮 `icon.svg` 會連帶動到 `apple-touch-icon` 的幾何，也就是動到 §3 那條約束，所以內縮只作用在這一個輸出。產出時會量並在越界時印出該用的倍率，倍率的通式是 `目前scale × (安全半徑 ÷ 實測半徑)`——直接用比值只在目前 scale 為 1 時才對。

**兩個 sharp／libvips 的陷阱**（產出腳本已避開，改動時別踩回去）：

- **`flatten` 在 `extend` 之前執行，不照呼叫順序。** 用透明色 extend 再 flatten，會得到一張「中央不透明、外圈一圈透明」的圖，而且**不會報錯**、console 輸出看起來完全正常。所以 extend 的 background 要自己帶最終底色。
- **libvips 嗅探 `<svg` 的視窗大約只有 1KB。** 檔頭註解太長會讓 sharp 回 `Input file contains unsupported image format`，而 XML 完全合法、錯誤訊息完全不指向長度。`public/icon.svg` 的說明因此寫在根元素**裡面**。

## 7. 驗證方式

Liquid Glass 只能實機觀察，模擬器與桌面瀏覽器都無法代替。

1. **要比較多個版本時，把它們放在不同網址各自加到主畫面。** iOS 會快取 web clip icon，逐版覆蓋就會看到舊圖而誤判；不同網址各自是獨立的 web clip，可以並排比較，也不必先移除舊的。本機起一個靜態伺服器、用 LAN IP 加到主畫面就夠了，**但不要用 Vite dev server——它的 SPA fallback 會把子目錄網址吃掉，回傳 App 本身的 `index.html`，於是三個測試頁會拿到同一個圖示。**
2. 只測一個版本而要覆蓋時，**先移除主畫面上的舊圖示再重新加入**。
3. 判準看背景色：**深色 = 有效，純白 = 失效**（§2）。
4. 比對 **Light／Dark／Clear／Tinted** 四種外觀。
5. 分不清立體感是系統加的還是圖檔自己畫的時，切到 **Tinted**：分層圖示會重新渲染並保留深度，烘死在 PNG 裡的高光只會變成一坨單色。

## 8. 已知限制

- **PWA 沒有官方的分層路徑。** Apple 開發者論壇上關於 iOS 26 PWA 圖示外觀的提問至今沒有官方回覆，也沒有對應的 Safari 釋出說明。本文件的條件全部來自實機觀察，不是文件化的行為，iOS 改版後要重驗。
- **機制未知。** 空腔內周長是預測器不是機制，不要當成 iOS 內部在算的東西。
- **PWA 無法指定 Clear 外觀。**
- **16×16 favicon 會失去細節。** 縫線在該尺寸看不見，星星縮成角落的亮點。
- **產出檔直接進版控。** GitHub Pages 部署不跑 icon 產出步驟，改圖後必須手動跑 `npm run icons:generate` 並 commit 產出檔。
